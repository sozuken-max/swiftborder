# Evaluation-integrity overhaul: causal features, DM/HAC + day-block significance, fixed-window BQML audit, hardened fetchers and camdetect

This change rebuilds the Layer B evaluation so that every reported number comes from a causal, out-of-sample protocol. It also records provenance in a versioned `run.json`. The offline XGB pipeline now uses raw labels, a persistence value taken at the forecast origin, calendar/D-1/D-7 features that are known at the origin, and backtest days after the split. `significance.py` swaps the iid t-test for an HLN-corrected Diebold–Mariano test with Newey–West HAC, an overlapping day-block bootstrap within direction groups, and Holm. The decision needs both DM and CI. New modules add a pandas rebuild of `v_training_set` with weather and camera joins (`features.py`), a rolling-origin joined experiment (`joined.py`), a Layer A scorer, and a camera backfill. The Causeway fetchers write complete days only, and `camdetect` gains input validation and a reusable `detect_frame()`.

The core formulas are correct: HAC Bartlett weights, the HLN factor, the one-sided p directions, moving-block start positions, and Holm monotonicity all check out. So do the fold boundaries, lag/label alignment, and UTC/SGT day handling. The main problems are provenance and how claims are stated.

Watch for: the promoted `run.json` code fingerprint does not match the working tree (**confirmed**). `docs/evaluation.md` cites a parity row count that is not in `run.json` (**confirmed**). The 2-hour forecast is joined by NEA *issue* time instead of data.gov *acquisition* time (**likely** small look-ahead). Holm runs separately on each one-sided side, so the family-wise guarantee is 2α, not the documented α (**confirmed**; no decision in the current run changes).

**Verdict**: NEEDS_CHANGES

## High-level view

The offline 60-minute XGB path (`timeseries_xgb.py`) is now causal end to end. The model input is forward-filled for at most 30 minutes and slew-capped causally. Labels are raw bin means `h` steps after the origin, the split is on target time, and backtest days are whole SGT days after the boundary. Persistence is `y_ffill` at the origin, so it can be up to 30 minutes older than "60 minutes before the label". The docs state the stricter version.

The significance module implements DM-HAC-HLN, a within-group moving-block bootstrap with one-day blocks, and Holm. The formulas are correct. Two statistical-reporting gaps remain. First, Holm is applied to each one-sided family separately, which bounds the error of any directional claim at 2α. Second, the HAC lag (about 9 bins) is far shorter than the daily dependence the bootstrap is built around, so DM p-values like 1e-214 overstate precision. The offline CI rests on 5 blocks, and the decision rule does not gate on block count.

`layer_b.py` pins a fixed window (13–30 Sep SGT) and refuses models whose creation or training-run start is on or after the window start. It scores every candidate on the same filtered rows. `joined.py` refits daily with a training cutoff of label end ≤ test-day start, which is correct for the `[t+30, t+40)` label. `features.py` reproduces the view's row-based `after_gap` and uses time-based lags. The forecast join filters on NEA's issue `timestamp`. data.gov's schema says the data was acquired at `update_timestamp`, which the fetcher discards.

The Causeway fetchers never write failed or partial days. A 200 with zero rows, or a first-page 404, is written as a final empty CSV and skipped on every later run.

`camdetect` stays compatible for requests that follow the documented format. The documented changes are `confidence=0` honoured, 400 on a malformed `date_time`, and 502 on a non-image frame. One undocumented edge exists: a present-but-empty body field no longer falls back to the query string.

The promoted report was made from a dirty tree. Its `code_sha256` (`e1a3054c…`) does not match `code_fingerprint()` of the current tree (`49a4b9c5…`). The docs say that hash "identifies the sources", which is not true for what is checked in.

### Report provenance and the "numbers only from run.json" rule

`provenance.git_dirty = true` and `SOURCE_RUN.json` record the `--allow-dirty` override, and the docs say so. The weaker guarantee is the hash. `code_fingerprint()` hashes `eval/*.py` and `sql/**/*.sql`. Both the system Python and `.venv` (3.11.9, the run's interpreter) give `49a4b9c5…` for the current tree, but `run.json` says `e1a3054c…`. File mtimes do not show edits after the run, so the difference cannot be traced to a specific file. Either way, the committed report cannot be tied to the committed code. Promotion should also refuse a run whose fingerprint differs from the working tree, or at least warn.

On claims: every table in `docs/evaluation.md` §1–§3, `findings.md` items 3/4/6, and the README results sentence match `run.json` to the stated precision. That includes the 63-comparison slice family and the per-slice statements about `lin_h30` and `xgb_h30`. The exception is the parity sentence in §2. The `features.py --parity` output is printed to stdout and never stored, and 7,180 equals `rows_scorable`. `docs/inventory.md` reports a different check ("0 of 3,572 per direction", which is 7,144 combined), which adds to the confusion. The "CUSTOM split on 11–12 Sep" and "5–30 Sep" fetch window are GCP or local facts, not run.json numbers. They are acceptable if they are sourced to `inventory.md`.

### Diebold–Mariano, bootstrap and Holm in `significance.py`

The formulas checked against the brief are correct: Bartlett weights, the HLN factor, one-sided p directions, block start range, percentile bounds, Holm monotonicity, and the SGT day-boundary offsets passed by each caller. Three reporting issues remain.

Holm is applied to `dm_pvalue` and to `dm_pvalue_reference` as two families. Under the global null, P(any "challenger" claim) ≤ α and P(any "reference" claim) ≤ α, so any false directional claim is bounded by 2α. The CI half of the conjunction is not multiplicity-adjusted, so it does not close the gap. Re-running the decision on `run.json` with Holm over two-sided `2·min(p_c, p_r)` changes none of the 91 decisions. The fix is cheap and makes `docs/evaluation.md:47` true.

The HAC lag follows the NW(1994) rule: 9 for n = 5,184, 8 for 2,592, 11 for the offline 1,428 at h = 12. Traffic loss differentials have daily structure, which is why the bootstrap block is one day. A 90-minute bandwidth likely underestimates the long-run variance. The joined `xgb[maps] vs maps_typical` p = 2.8e-214 is a symptom. Decisions stay protected by the CI requirement, but DM is presented as the primary test.

`blocks_per_resample` is recorded and documented as "coarse below ~10", but `decision` ignores it. The offline hold-out (5 blocks) and the weekend slices (5 per direction) get full "challenger"/"reference" labels. The `MY_TO_SG/day_type=weekend` CI `[0.196, 0.661]` around a mean of 0.32 shows how lumpy a 5-block percentile interval is.

### Offline XGB alignment (`timeseries_xgb.py`)

No off-by-one was found in lags, labels, D-1/D-7 lookups (guarded by the `h < 1 day` assertion) or backtest-day selection. The remaining gap is the persistence definition. `out["persistence"] = y_ffill[origins]` returns the last raw bin within the previous 6 bins, so the effective lag is 60–90 minutes. The docs and the brief say "exactly 60 minutes before the label". Model inputs use the same ffill, so the comparison is fair, but the sentence should match the code.

### Forecast availability in the causal feature builder (`features.py`)

The forecast join filters on `issue_timestamp ≤ asof`, and `issue_timestamp` comes from `item.timestamp`. `Causeway/2hourWeatherForecast.json` defines `timestamp` as "Time forecast was issued by NEA" and `update_timestamp` as "Time of acquisition of data from NEA". The example lag is about 6 minutes. The fetcher dedups on the full record tuple, so revised texts that share an issue timestamp both survive. `filter_area_forecast` then keeps whichever it reads last. Both effects can put information after `asof` into `fc_rain` / `fc_heavy`. The weather-null result is robust in direction, since leakage can only help weather. The causality claim in `docs/evaluation.md:176` needs the fix, and so does any future "weather helps" result.

`add_camera` fails on pandas 2.x (object-dtype `to_numpy()` on tz-aware Series). It passes on the pinned pandas 3.0.6, which CI installs.

### Empty days in Causeway completeness (`datagov.py`)

A first-page 404 or a zero-row 200 writes an empty final CSV marked `no_data`, and the next run reports it as "already complete". If data.gov is late or briefly empty for a recent day, that gap becomes permanent unless someone re-runs with `--overwrite`. Unexpected payload shapes (for example `data` as a list) raise `AttributeError`. That aborts the whole run, not just the day, but nothing partial is written.

### camdetect compatibility (`camdetect/main.py`)

The service is still unauthenticated, as already recorded in `inventory.md` and `findings.md`. The only new security-relevant items are improvements: `date_time` validation also blocks header injection via `X-Frame-Datetime`, and upstream error detail is no longer echoed.

These documented changes alter output for some existing callers:

- `confidence: 0` in the body is now honoured.
- Minute-precision or offset `date_time` values that data.gov may accept now get a 400.
- Non-image frames now return 502 where they used to degrade to "Unknown".

One undocumented change: `_param` falls back to the query string only when the body value is `None`, so `""` in the body now overrides a query value. Before, `""` fell through. For `date_time` the request then returns the current frame without any error.

### Test coverage

The eval (125), camdetect (40) and Causeway (26) suites pass on the pinned `.venv`.

Not tested:

- Holm across both one-sided sides against the stated FWER.
- DM sensitivity to HAC lag.
- Decisions with fewer than 10 blocks.
- Forecast selection by acquisition time.
- A `no_data` day recovering on a later run.
- `_param` with empty-string body values.
- `promote_report_run` rejecting a `code_sha256` that differs from the tree.
